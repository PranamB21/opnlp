# Real-time meeting & lecture assistant

Live speech-to-text with speaker labels, turned into structured meeting notes by an LLM:
a **topic timeline**, **key points**, and **action items** that update while people talk,
plus an **End meeting** button that summarizes the session and posts it to Slack.

Built for an open-ended college project. The speech side is
[WhisperLiveKit](https://github.com/QuentinFuxa/WhisperLiveKit) (unmodified Python, extended
web UI); everything NLP lives in a separate FastAPI service that talks to it over its public
WebSocket protocol.

```
 microphone / tab audio
        │  (PCM or WebM frames)
        ▼
┌──────────────────────┐   audio frames    ┌─────────────────────────────┐
│  Dashboard (browser) │ ────────────────▶ │  NLP service  :8001         │
│  transcript +        │                   │  • WS bridge → ASR          │
│  topic timeline +    │ ◀──────────────── │  • rolling-window buffer    │
│  key points +        │  transcript +     │  • LLM structured extraction│
│  action items        │  nlp updates      │  • meeting state + Slack    │
└──────────────────────┘                   └──────────┬──────────────────┘
                                                     │ audio proxy
                                                     ▼
                                          ┌─────────────────────────────┐
                                          │ WhisperLiveKit  :8000       │
                                          │ faster-whisper + Sortformer │
                                          │ diarization + VAD           │
                                          └─────────────────────────────┘
```

## What runs

| Component | Port | Entry point | Role |
|---|---|---|---|
| WhisperLiveKit ASR + diarization | 8000 | `run_asr.sh` → `wlk serve ... --diarization` | Timestamped, speaker-attributed transcript over `ws://…/asr` |
| NLP microservice | 8001 | `run_nlp.sh` → `python -m nlp_service` | Transcript bridge, rolling-window segmentation, LLM extraction, meeting state, Slack, dashboard host |
| Dashboard | 8000 or 8001 | `whisperlivekit/web/live_transcription.*` | Live transcript + 3 insight panels + End meeting button |

The NLP service is a **separate process with no imports from `whisperlivekit`**; the only
coupling is the documented WebSocket JSON payload. You can rewrite prompts, windowing, or swap
the provider without touching the ASR install.

## Running it

### Every time (one command)

```bash
./start.sh
```

Starts both services, waits until they answer, then prints:

```
Dashboard:   http://localhost:8001/     <- use this one
ASR-only UI: http://localhost:8000/
```

Open the dashboard URL, click the record button, allow the microphone, and talk. `Ctrl+C` stops
both services; if you closed the terminal, `./stop.sh` stops whatever is listening on ports
8000/8001.

Environment variables (API key, Slack webhook, window sizes) can be exported first or put in a
`.env` file next to `start.sh` — copy `env.example` to `.env` and edit it:

```bash
cp env.example .env      # then fill in ANTHROPIC_API_KEY / SLACK_WEBHOOK_URL
./start.sh
```

### Same thing in two terminals

```bash
./run_asr.sh     # terminal 1: WhisperLiveKit ASR + diarization (port 8000)
./run_nlp.sh     # terminal 2: NLP service + dashboard (port 8001)
```

Either URL shows the same extended UI: **http://localhost:8001/** is served by the NLP service,
**http://localhost:8000/** is served by WhisperLiveKit and points its WebSocket at the NLP
service automatically.

### First time only (already done in this checkout)

```bash
cd WhisperLiveKit
git submodule update --init --recursive     # qwen3-asr-causal stub is referenced by pyproject
uv sync --python 3.12 --extra cu129 --extra diarization-sortformer
cd ..
```

This creates `WhisperLiveKit/.venv`, which both services use. It needs Python 3.12 (the system
default here is 3.14, which the project does not support). First start also downloads the Whisper
and Sortformer weights from Hugging Face, so run it once with network access before the demo.

No microphone? Replay the bundled two-speaker meeting through the whole pipeline:

```bash
./run_demo.sh                    # real-time replay + summary + Slack preview
./run_demo.sh --speed 2 -v       # faster, verbose
```

`demo_audio/meeting.wav` is generated by `demo_audio/build_demo_audio.py` (edge-tts, two voices,
16 scripted turns, ~109 s). It is also a regression fixture.

### Suggested demo flow (2 minutes)

1. Show `http://localhost:8000/` with `--diarization`: talk, point out the speaker badges.
2. Switch to `http://localhost:8001/`: after ~20-40 s the topic timeline, key points and action
   items appear on their own; keep talking and they grow.
3. Click **End meeting & send to Slack**: summary panel appears; with `SLACK_WEBHOOK_URL` set the
   message lands in the Slack channel (otherwise the preview is shown locally).
4. If the room has no usable mic, run `./run_demo.sh --speed 2 -v` and show the same panels
   filling from the pre-recorded two-speaker meeting.

## Pipeline details

**1. ASR + diarization (given).** WhisperLiveKit streams a full-state JSON frame every ~50 ms:

```json
{"status": "active_transcription",
 "lines": [{"speaker": 2, "text": "About two seconds of lag", "start": "0:00:18.64", "end": "0:00:22.10"}],
 "buffer_transcription": "…", "buffer_diarization": "…", "remaining_time_transcription": 0.4}
```

Important property: **a line grows in place** — same `start`, later `end`, longer `text`. The
bridge keys segments by `(speaker, start)` and applies growth to the pending window until that
line is cut into an analyzed window. (Keying by `(start, end)` instead turns one sentence into a
dozen prefix fragments; that bug was caught and fixed during verification — see
`test_window_grows_line_until_cut_then_ignores_revisions`.)

**2. Rolling window.** Committed lines accumulate until one of:

| Trigger | Default |
|---|---|
| window duration reached | `NLP_WINDOW_SECONDS=40` |
| pause between turns | gap ≥ `NLP_PAUSE_GAP_SECONDS=2.5` s and window ≥ min |
| speaker change | different speaker and window ≥ `NLP_MIN_WINDOW_SECONDS=20` s |
| hard cap (LLM too slow) | `NLP_MAX_WINDOW_SECONDS=90` |

A worker task consumes windows sequentially, so a slow LLM call never blocks audio or
transcription. The queue is bounded (8) and drops the oldest window if extraction falls behind.

**3. LLM extraction.** One call per window with `SYSTEM_PROMPT` from `nlp_service/prompts.py`,
JSON-only output, and `null` for unknown owner/deadline. Response is normalized
(`models.normalize_extraction`) — renamed fields, flat bullet strings, and string action items all
degrade gracefully. Results merge into a single meeting state: topics are de-duplicated by label
and overlap, action items by normalized task text (growing prefixes of the same sentence
collapse into the longest wording).

**4. End meeting.** `POST /api/end` flushes the last window, asks the model for a summary plus
decisions, and posts the summary + action items to `SLACK_WEBHOOK_URL`. Without a webhook it
returns a rendered preview, so the button is demoable offline.

## The three open-ended choices

### 1. ASR engine — WhisperLiveKit's default streaming stack (`faster-whisper` base + SimulStreaming)

*Why:* real-time streaming needs incremental decoding with stable partials, which vanilla
Whisper-on-chunks does not give (it cuts words at chunk boundaries and loses context).
WhisperLiveKit's LocalAgreement/SimulStreaming policies already solve this, and its server,
protocol, and UI were the assignment's base. `base` was chosen to leave VRAM for diarization on
a 6 GB RTX 4050; `WLK_MODEL=small` or `medium` is a one-word upgrade on better hardware.

*Trade-off, honestly stated:* a streaming `base` model is less accurate than an offline
`large-v3`, especially on proper nouns (the demo transcript renders "README" as "Readney").
Diarization boundaries also split a few sentences across speaker turns when speakers overlap.

*Alternatives considered:* Deepgram/AssemblyAI (costs money, needs network, same wrapper problem),
`whisper.cpp` (no built-in diarization), cloud speech + offline re-transcription (adds minutes of
latency, defeats "real-time").

### 2. Noise handling — WhisperLiveKit's built-in VAD (+ diarization segmentation)

*Why:* Silero VAD gates silence before it reaches the ASR (default, `--no-vad` disables), so
background hum between utterances is not decoded into hallucinated text. Diarization segmentation
then gives clean speaker turn boundaries, which also serve as free sentence boundaries for the
windowing stage. This is "the platform already implements the noise-robust subset properly; do not
add a second, weaker gate".

*Trade-off:* VAD reduces noise-driven hallucinations but does not remove steady broadband noise
(fans, HVAC) inside a speech region. Adding a denoiser (e.g. DeepFilterNet) was deliberately out
of scope for a few-day project — it adds a model, latency, and new failure modes.

### 3. NLP method — cloud LLM structured extraction over rolling windows

*Why:* topic segmentation, key points, action items, *and inferred owners/deadlines* need
semantic understanding. An LLM in a strict JSON contract does all four in one call; classical
alternatives need a separate sentence splitter, embedding model, clustering step, and hand-written
rules for owners ("I'll…" → speaker) and deadlines ("by Friday") that generalize badly.
The cloud call also keeps the laptop free for ASR/diarization GPU work.

*How the "just a wrapper" objection is answered:* the LLM is one stage in a pipeline the project
owns — the bridge protocol, growth-aware dedupe, boundary detection, incremental merge/dedupe of
topics and action items across windows, tolerant JSON normalization, meeting state, and Slack
delivery are all original code. Swapping providers (Anthropic ⇄ OpenAI ⇄ offline heuristic) is one
environment variable, which is the decoupling the brief asked for.

*Trade-off:* ~2–4 s and some cost per window (roughly one call per 20–40 s of speech), plus
reliance on an API key during the demo. Mitigations: `NLP_LLM_PROVIDER=mock` runs a local
heuristic extractor that produces the same JSON shape, so the dashboard, windowing, dedupe, and
Slack path stay fully demoable offline.

## Providers

`NLP_LLM_PROVIDER=auto|anthropic|openai|mock` (default `auto`: Anthropic key → OpenAI key → mock).

| Env | Default |
|---|---|
| `ANTHROPIC_MODEL` | `claude-sonnet-4-5` |
| `OPENAI_MODEL` | `gpt-4o-mini` |
| `SLACK_WEBHOOK_URL` | unset → preview only |
| `WLK_WS_URL` | `ws://localhost:8000/asr` |

See `env.example`. API calls are plain `httpx` POSTs (`nlp_service/extractor.py`), no vendor SDK.

## HTTP / WebSocket API

| Endpoint | Purpose |
|---|---|
| `GET /` | Dashboard (extended WhisperLiveKit UI) |
| `WS /asr` | Audio relay + transcript subscription; emits `{"type":"nlp","event":"update"\|"status"\|"final"\|"error"}` frames |
| `GET /api/state` | Current topics / key points / action items snapshot |
| `POST /api/end` | Flush, summarize, post to Slack, broadcast `final` |
| `GET /api/export` | Markdown notes |
| `POST /api/reset` | Clear the meeting |
| `POST /api/ingest` | Push transcript lines without audio (integration testing) |
| `GET /health` | Provider, clients, windows, segments |

## Notes and known limitations

* **Idle sessions:** WhisperLiveKit closes a native `/asr` session after
  `--session-idle-timeout` seconds without audio (default 60 s). `run_asr.sh` sets it to `0`
  (disabled) so a paused lecture does not lose the meeting. If the ASR session does end, the
  bridge tells the dashboard and closes the socket so the UI can reconnect.
* **NLP service down:** the dashboard detects the failed bridge connection, switches its WebSocket
  to WhisperLiveKit's `/asr` directly, and shows "NLP offline"; transcription keeps working with
  empty insight panels.
* **Transcript history** is not replayed into the browser after a page refresh: panels repopulate
  from `/api/state`, but the transcript pane only shows the current ASR session. `GET /api/export`
  returns the full text.
* **One meeting at a time.** Ending a meeting (or the ASR session finishing) marks the notes as
  complete; the next recording that starts from t=0 clears the panels for a fresh meeting. A
  reconnect in the middle of a meeting keeps the notes.
* **Overlapping speech:** Sortformer labels the dominant speaker per frame; simultaneous talking is
  attributed to one speaker.
* **Cut mid-sentence:** when a duration/speaker-change cut lands inside a still-growing line, the
  tail of that line reaches the dashboard but not that window's analysis.
* **`/api/ingest`** shares the live pipeline if a dashboard session is open; otherwise it creates a
  detached pipeline. It is a testing hook, not part of the demo path.

## Verification performed

* Stage 1 alone: 109 s demo audio streamed into `wlk serve --diarization`; output had per-line
  timestamps and alternating `speaker` 1/2 matching the two synthesized voices.
* Stage 1+2 headless (`demo_audio/feed_demo.py`): 5 windows, topics/key points/action items
  extracted, `/api/end` summary + Slack preview returned.
* Dashboard in Chromium (screenshots in `verify/`): the page's own WebSocket carried the demo
  audio through the bridge to the ASR and back — transcript with speaker badges and timestamps,
  panels filling in live, End meeting producing the summary + Slack preview, light/dark themes,
  desktop (1440x900) and mobile (390x844) layouts, and the NLP-offline fallback.
* Resource use on the test laptop (RTX 4050, 6 GB): `base` + Sortformer diarization peak at
  ~1.8 GB VRAM, leaving room for `WLK_MODEL=small`.
